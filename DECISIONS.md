# Decisions

Choices made while building Paisa Pulse, with the reasoning, so they can be revisited.

## D1. Version policy: "latest stable, nothing released in the last 14 days"

- Cutoff for Phase 1 was **2026-10-10** (build date 2026-10-24).
- **Exception: Expo SDK patch releases.** `expo-doctor` (a required check) insists on
  the newest patch of every SDK package (e.g. `expo` 57.0.31, released 2026-10-21). The
  only way to keep older patches is `expo.install.exclude`, which silences the check.
  Patch releases inside an SDK that has been stable for four months are bug fixes, so we
  take them. Majors and minors of everything, and all non-Expo libraries, still follow
  the 14-day rule.
  _To revert:_ pin older patches and add them to `expo.install.exclude` in
  `apps/mobile/package.json` (doctor will then skip them).

## D2. Expo SDK 57, not 58

SDK 58.0.0 shipped 2026-09-29, but it targets React Native 0.88, whose stable 0.88.0
release is from 2026-10-15 (9 days old). Every SDK 58 patch before the cutoff bundles
`react-native@0.88.0-rc.x`, a release candidate. Running SDK 58 therefore means either
a pre-release or a too-new release. **SDK 57 (React Native 0.86.3, React 19.2.3)**
satisfies both rules. Upgrade to SDK 58 once RN 0.88.0 is older than 14 days
(on or after 2026-10-29): `npx expo install expo@^58 --fix`.

## D3. Toolchain

| Tool | Version | Why |
| --- | --- | --- |
| Node | 24.21.0 LTS (`.nvmrc`) | Expo 57+ requires Node ≥ 22.13; machine had Node 20 (EOL). 24.22.x was too new. |
| .NET SDK | 10.0.401 (runtime 10.0.12) (`apps/api/global.json`) | .NET 10 LTS. 10.0.13 / SDK 10.0.402 was too new. Installed to `~/.dotnet` with the official `dotnet-install.sh` (no sudo). |
| JDK | 17 (existing) | Required by the Android Gradle Plugin used by RN 0.86. |

## D4. No JS workspaces at the repo root

`apps/mobile` owns its `node_modules` and lockfile; the root `package.json` only holds
convenience scripts. npm workspace hoisting is a known source of broken Gradle paths and
duplicate native modules in React Native apps, and the API is .NET, so a JS workspace
gains nothing today. If a shared TS package is needed later (e.g. shared zod schemas),
revisit.

## D5. Continuous Native Generation

`apps/mobile/android/` is generated by `expo prebuild` and is git-ignored. Native changes
go through `app.json`, config plugins, or the local Expo module in
`apps/mobile/modules/` (Phase 4). The brief's `/native` folder is therefore
`apps/mobile/modules/sms-reader`, as the brief itself allows ("inside the mobile app's
modules folder").

## D6. Install scripts

npm 11 blocks dependency install scripts until approved. Two were denied (recorded in
`allowScripts` in `apps/mobile/package.json`):
- `unrs-resolver`: a fallback downloader; the native binding already ships as an optional dependency.
- `fsevents`: ships a prebuilt binary; the script is only a node-gyp fallback.

## D7. Test runner on .NET 10

.NET 10's `dotnet test` no longer runs VSTest for xUnit v3 projects. The API opts in to
Microsoft.Testing.Platform in `apps/api/global.json`, so `Microsoft.NET.Test.Sdk` and
`xunit.runner.visualstudio` are not needed.

## D8. Code analysis

`AnalysisLevel=latest-recommended` + `TreatWarningsAsErrors`. Rule CA1707 (no underscores
in member names) applies to tests too, so test names are PascalCase
(`ParseKeepsEqualsSignsInsideValue`) rather than `Parse_Keeps_...`. No rules are disabled.

## D9. `.env` loading

A ~60-line in-repo loader (`Configuration/DotEnv.cs`) instead of a NuGet package: it walks
up from the working directory, never overrides real environment variables, and never logs
values. Precedence: real environment → `.env` → `dotnet user-secrets`.

## D10. No Docker

Per the user, Docker/Testcontainers are out. API integration tests (Phase 7) will use an embedded `mongod`
binary instead, so they still exercise the real MongoDB driver and indexes.

## D11. SMS dates

`occurredAt` is the SMS receive timestamp, not a date parsed from the body: banks send alerts within
seconds, and body dates vary by bank and usually omit the time.

## D12. Dedupe details

- `dedupeHash = sha256(upiRef)` if present, else `sha256(amount|last4|minuteBucket)` (as specified). Manual
  entries hash a random id, so they never collide.
- Window rule (±3 min, same amount and direction): same last4 → duplicate; different last4 → not; otherwise a
  loose merchant match, or an SMS vs app notification pair (notifications rarely carry the account) → duplicate.
- Two different references are always two payments.
- On a window match the existing row is enriched (upiRef, last4, balance) and keeps its id and hash.

## D13. What counts as spend

Debits that are not excluded ("Not an expense") and not in a fixed category (Rent & EMI; those are budgeted
via fixed expenses). Credits never reduce spend. IMPS/NEFT debits and phone-number VPAs default to
"Transfers to people"; credits are "Other".

## D14. Budget rounding and freezing

`todayBudget` is rounded half-up to the paisa (5000000/30 → 166667 = ₹1,666.67). It is frozen per IST date in
`daily_budgets` on first access. Because it only depends on spending *before* today, freezing at 14:00 gives
the same number as 00:00. Changing the profile clears today's and future frozen budgets.

## D15. Live SMS while the app is closed

Native receivers always enqueue first, then either emit an event (JS running) or start a headless JS task.
If Android blocks a background service start, the queue is drained at the next app start. Raw text lives
only in that app-private queue until parsed.

## D16. SMS permissions and Play Store

READ_SMS/RECEIVE_SMS are restricted on Google Play (only default SMS apps or approved exceptions). This
build is intended for sideloading/personal use; a Play release would need a permissions declaration or
notification-only mode.

## D17. Repository tests use node:sqlite

Repositories depend on a small `SqlDb` interface matching expo-sqlite. Tests use Node 24's built-in
`node:sqlite`, so real SQL (constraints, ON CONFLICT, LIKE escapes) is exercised without a native module.

## D18. Colour tokens for text vs graphics

The spec's light-theme accent, amber and coral (#3E8E6B, #B07C2A, #B85A4A) are below 4.5:1 as body text on
the light background. They are kept for graphics (ring, bars, donut, large numbers), and separate `*Text`
tokens (#2F7356, #85601F, #9E4536) plus `accentFill` for buttons are used wherever text sits on them. In dark
mode both sets are the spec colours. A unit test enforces the ratios.

## D19. Number roll-up runs on the JS thread

The ring animates on the UI thread (Skia + Reanimated). The rolling number uses a short requestAnimationFrame
tween so it stays a real `<Text>` (screen readers read the final value via accessibilityLabel) without
`TextInput` hacks or `any` casts. It is ~40 frames per change and is skipped entirely with Reduce Motion.

## D20. No looping animations; skeletons are static

Loading states are static placeholder blocks faded in once (no shimmer), per "no infinite looping animations".

## D21. Sample data mode in Phase 5

Pulled forward from Phase 9 so the screens can be seen without real bank SMS. It writes a fixed, seeded set of
payments for the current cycle and a sample salary/fixed-cost profile; "Delete all my data" clears it.

## D22. Day rollover

The frozen daily budget is created on first access of each IST day, and the app refreshes on resume and at
midnight (`useTodayKey`), so "00:00" semantics hold without a background job.

## D23. HTTPS enforcement and CORS lockdown

Production enforces HTTPS (`UseHsts` and `UseHttpsRedirection`). CORS is locked down: the phone app uses native
networking and does not require browser CORS, so CORS is off unless explicit, non-wildcard origins are specified in
`CORS_ORIGINS`. In development mode, plain HTTP is permitted so local phones and emulators (via USB `adb reverse` or
local Wi-Fi IP) can communicate without Android untrusted TLS certificate errors.

## D24. Dockerless real MongoDB integration tests

Per requirement D10, Docker/Testcontainers are excluded. Integration tests use `Mongo2Go` (v5.0.0) which bundles
native macOS Apple Silicon (arm64) `mongod` binaries. The binaries search root is explicitly pointed to the NuGet
tools directory to avoid macOS TCC folder permission prompts when enumerating parent folders.

## D25. Server-side transaction idempotency and immutable _id preservation

Transactions are scoped strictly by authenticated `userId` and deduplicated by a unique compound MongoDB index on
`(userId, dedupeHash)`. Batch uploads via `/api/v1/transactions/sync` execute atomic `UpdateOneAsync` with `SetOnInsert`
for `_id` and initial fields. This guarantees that re-uploading transactions—even with newly generated client IDs
(e.g., after an app reinstallation)—updates metadata without attempting to modify MongoDB's immutable `_id`.

## D26. Hangfire nightly summaries job

Hangfire schedules `DailySummaryJob` at midnight IST (`0 0 * * *` in Asia/Kolkata timezone). The job aggregates
discretionary spend, yesterday's budget, amount spent, and top category, writing the results to `dailySummaries`.

## D27. Hashed refresh tokens

Refresh tokens are stored in MongoDB as SHA256 hashes (`RefreshTokenHash`), rather than plain text. A database
breach does not expose usable refresh tokens to attackers.

## D28. Fail-fast secrets and index startup enforcement

`JWT_SECRET` must be at least 32 characters and never has a hardcoded fallback value; missing secrets abort startup
immediately with actionable messages. MongoDB index initialization is mandatory: failure to create the indexes (including
the deduplication index) aborts startup immediately rather than running degraded.

## D29. Node.js API replaces the .NET API

`apps/api` (.NET 10) was removed; `apps/api-node` (Express 5 + MongoDB driver, TypeScript strict) is the only
backend, so the whole repo is one language and one toolchain. It keeps the same `/api/v1` contract the mobile app
uses, with one shared IST budget-rule module (`src/domain.ts`, a copy of the mobile rules) for insights and the
nightly job (`node-cron` at 00:00 Asia/Kolkata replaces Hangfire). Default database stays `paisapulse`.
D7 (.NET test runner), D26 (Hangfire) and the .NET rows in D1 no longer apply. Tests use
`mongodb-memory-server` (embedded mongod, no Docker), replacing Mongo2Go (D24).

## D30. Admin dashboard talks to the API through a server-side key

The admin app (`apps/admin`, Next.js) calls `/api/v1/admin/*` only from its own server routes, sending
`x-admin-key: ADMIN_API_KEY`. The key is never shipped to the browser. Without `ADMIN_API_KEY` the API disables the
admin endpoints (503) instead of leaving them open. The dashboard shows a banner whenever it falls back to sample
data, and edits made in the dashboard are labelled "this view only" because the admin API is read-only.

## D31. Carry-forward daily allowance and once-a-day cards

Replaces the fixed allowance of D14. A day's allowance is the cycle's money left before the day (salary − fixed
expenses − savings, prorated for a cycle joined part-way, minus net spend since the cycle or budget start) ÷ the
days left including it, never below 0. Unspent money raises every remaining day a little and an overspend is
shared across them, so no single day is hit hard; nothing carries across payday. Because it depends only on
spending *before* the day, 00:00 and 14:00 still agree. Today's row in `daily_budgets` is recalculated on every
read (a payment recorded late for an earlier day moves it); past days keep their stored value. The snapshot also
gives `nextDaysAveragePaise`: the daily average for the days after today if nothing more is spent today. The
Node API's daily summary uses the same rule.

The morning card (first open of the day) and night card (from `nightTime`, default 9 pm) are claimed with
`markOnce('card:<kind>:<date>')` in `notification_log`, so each shows at most once per IST day across restarts and
racing checks; no migration. They pop up only on the four main tabs, never during add/edit or onboarding, and are
hidden while the app lock is up (an RN `Modal` would otherwise draw over it). The phone computes the numbers
locally because the app works without an account; the server mirrors the formula for synced users.

## D32. Performance optimization across storage, queries, components, and API

Optimizes end-to-end responsiveness and resource efficiency while preserving all business rules and designs:
1. **Asset optimization**: Deleted 4 unreferenced raw PNG assets in `apps/mobile/assets/Bg/` totaling ~6.45 MB, leaving only compressed ~100 KB WebP/JPG dynamic backgrounds (`morning.jpg`, `afternoon.jpg`, `evening.jpg`, `night.jpg`).
2. **SQLite database indexes**: Added migration v7 introducing covering composite indexes:
   - `idx_tx_spend_calc` on `(occurred_at, is_excluded, direction, category, amount_paise)` enabling index-only covering scans for `spendBetween` and `dayResults` without accessing row pages.
   - `idx_tx_cat_occurred` on `(category, occurred_at DESC)` for fast category filtering in `listTransactions`.
   - `idx_tx_sync_updated` on `(sync_state, updated_at)` and `idx_del_tx_sync` on `(sync_state, deleted_at)` eliminating file sorts in pending sync queues.
3. **TanStack Query caching**: Increased default `staleTime` to 30s in `_layout.tsx`, 60s for static entities (`profile`, `settings`), and 5 minutes for historical completed cycles (`useInsights(offset > 0)`). Mutations immediately purge caches via `invalidateAll()`.
4. **UI component memoization**: Memoized `TransactionRow`, `SwipeRow`, `TodayContent`, `HeroCard`, `StatusCard`, `AffordLauncherCard`, `TodaySpending`, and `MonthGlance` using `React.memo`, stable `renderItem` callback, and memoized category breakdown computations.
5. **MongoDB backend indexing and pooling**: Configured optimal connection pooling (`maxPoolSize: 50, minPoolSize: 5, maxIdleTimeMS: 30000`) and compound indexes for `{ userId: 1, id: 1 }` (unique), `{ userId: 1, category: 1, occurredAt: -1 }`, and `{ userId: 1, dueDay: 1 }`, plus projection pruning on insight queries.

## D33. Second-stage performance profiling, Skia memoization, and animation throttling

1. **Animation frame throttling**: In `useCountUp`, added an early exit when `from === target`. Previously, parent re-renders caused new 400ms `requestAnimationFrame` loops even when numbers were static, flooding the JS event loop with unnecessary setState calls.
2. **Skia canvas and chart memoization**: Memoized `DonutChart` and `BudgetRing` with `React.memo`, preventing recreation of Skia path builders and GPU pipeline re-evaluations during unrelated updates. In `BreakdownCard`, memoized `slices` with `useMemo` to keep slice references stable across renders.
3. **Insights hierarchy memoization**: Memoized `InsightsContent`, `SummaryCard`, `BreakdownCard`, `Patterns`, `PatternRow`, `Highlights`, and `SafeToSpendCard` with `React.memo`.
4. **DeviceSync race condition cleanup**: Removed redundant duplicate `syncNow()` call in `AppState` change listener; `refresh()` already orchestrates `syncNow()` in its `finally` block once ingestion is complete.
5. **Query plan validation**:
   - SQLite verified with `EXPLAIN QUERY PLAN`: `spendBetween` confirmed to use `SEARCH transactions USING COVERING INDEX idx_tx_spend_calc`, reading 0 row data pages.
   - MongoDB verified with `explain('executionStats')`: `ix_transactions_userId_occurredAt`, `ix_transactions_userId_category_occurredAt`, `ix_fixedExpenses_userId_dueDay`, and `ux_transactions_userId_id` confirmed to serve their respective queries with zero in-memory sorting.

## D34. AI Money Assistant through OpenRouter, server-side and read-only

```yaml
decision:
  action: apps/api-node (new assistant route + services), apps/mobile (new /assistant screen)
  reason: answer money questions from the user's real numbers, without exposing an API key
  evidence: the API already holds synced profile, fixed expenses and payments per user (requireAuth),
            and mirrors the phone's budget maths in domain.ts
  risk: medium (new external dependency, cost)
  allowed_by_contract: true
```

1. **The key never leaves the server.** The phone calls `POST /api/v1/assistant/chat` with its
   access token; the API calls OpenRouter with `OPENROUTER_API_KEY`. No key, no assistant
   (503 "not configured"), and the rest of the API is unaffected.
2. **Numbers are computed, not generated.** `services/financialContext.ts` builds a compact summary
   for the signed-in user only (this cycle, last cycle, categories, safe-to-spend, bills, savings,
   recent payments without notes, VPAs or account numbers) with the same rules as the phone
   (`rollingAllowance`, `poolForCycle`, the Purchase Simulator tiers). The model is told to quote
   these figures and label anything else as an estimate. An amount in the question ("₹5,000") is
   simulated on the server so affordability answers use computed results.
3. **Read-only.** The assistant has no tools and cannot write anything; it can only suggest.
4. **Account required.** The data lives on the server only for signed-in users, so the phone syncs
   first and the screen asks people without an account to sign in. Sample data is never sent.
5. **Cost controls.** Per-user per-minute rate limit, a daily message and token quota (Mongo
   `aiUsage`, deleted with the account), one request at a time per user, at most 8 history turns
   and 1,500 characters per message, capped output tokens, upstream timeout, and the upstream
   request is cancelled when the phone disconnects.
6. **Streaming.** Server-sent events over the POST response (`Cache-Control: no-transform` keeps
   compression from buffering); the phone reads it with Expo's streaming `fetch`.
7. **Conversations stay on the phone** (SQLite `assistant_messages`, last 100 kept); the server
   stores no chat text and logs no message content.
8. **No looping animation (D20):** the "thinking" state is a static indicator; the streamed text is
   the progress.
